The `git ls-remote` semantics — load-bearing, paste the relevant excerpt into the prompt body for the executor:

```
$ git ls-remote <url> refs/tags/<tag>
<sha-of-tag-object>    refs/tags/<tag>
<sha-of-dereferenced-commit>    refs/tags/<tag>^{}
```

For an **annotated** tag, both lines are emitted: the first is the SHA of the tag object, the second is the SHA of the underlying commit. The agent MUST prefer the `^{}` line (the commit SHA) because that is what `git rev-parse` / the local `Tag` operation returns and what subsequent `git push` operations round-trip against. Comparing against the tag-object SHA is a silent correctness bug — the stage-1 prototype hit it on iteration one.

For a **lightweight** (un-annotated) tag, only the first line is emitted. In that case the tag-object SHA is the commit SHA, and the agent returns that line as-is.

For a **missing** tag, no line is emitted. The function returns `("", nil)`.

Read `/workspace/agent/github-releaser/Makefile` and the root `/workspace/Makefile.precommit` to understand the local `make test` and `make precommit` shapes (the service is `maintainer-agent-github-reaser`, so `cd agent/github-releaser && make test` and `cd agent/github-releaser && make precommit` are the relevant entry points).
